# M2-K13 — the kernel commits every `FiberTransition` and publishes none, so a plugin can poll the composition but never observe it

**Milestone:** M2 (harness-finding-driven; jinn-harness FINDINGS.md #40 and
#41) · **Owner:** kernel-dev · **Status:** ready · **Binding rules:** R1,
R3, R5, R9, R10, R11, R12, Laws 1/2/3 · **LOC ceiling (card-authoritative;
canonical meter = the M2-K3 numstat form over the surfaces this card names,
with R10's exclusion list applying in full — the card does not restate it
and never narrows it):** combined production net delta ≤560 across
`crates/jinnd-wasm/src`, `crates/jinnd-daemon/src`, `wit/plugin.wit`,
`contracts/jinn-introspect` · facade delta ≤30 · **Standing gates:** all

**THREAT MODEL (stated before round 1, per the standing law):** honest
plugins under ordinary composition — a catalog watching the tree it is
allowed to read, a listener that is slow, a listener that panics, a
listener that mounts halfway through another plugin's life. NOT a plugin
mining the event stream to learn about fibers it was never granted sight
of; that is the authority question below and it is acceptance, not threat
model. A plugin abusing a grant it was legitimately given is a named known
limit, not a blocker.

**STOP RULE (stated before round 1):** at most 4 rounds. After that,
anything open that is not a self-contradiction or an outright false
statement becomes a named known limit and the packet lands.

## Why

Two harness findings, one kernel gap, found by the LAST core-port seam —
the one whose whole job was making the composition legible to an operator.

**#40 — there is no lifecycle event surface at all.**
`jinn:introspect@0.2.0` is a pair of PULL operations (`entries()`,
`readiness()`), each answered from a snapshot. The kernel commits every
fiber transition to the ledger as `FiberTransition { fiber, from, to,
cause }` (`crates/jinnd-daemon/src/support.rs`, `sync_transitions`), and a
plugin holding `jinn:ledger` can read that record — but only by asking,
after the fact, on its own schedule. Nothing pushes. The one event bus
(`jinn:plugin` world, `interface events`) carries only what plugins
themselves emit; the kernel is not a publisher on it and there is no listen
topic for a lifecycle change.

**#41 — and the poll cannot see what the pull would have shown.** Measured
through the real pinned daemon: a restart triggered through the operator
API, the catalog read in a tight loop for the whole window, then the
kernel's own ledger read back. The kernel committed `Active → Unloading →
Pending → Loading → Active` with cause `ConfigChanged`. All 189 catalog
reads returned `active`. Three of the plugins seam's eleven readings —
`mounted`, `activating`, `interrupted` — name a fiber between two rests,
and no consumer at this pin can reach any of them.

**Why this is a kernel card and not a seam workaround.** The only event a
plugin could emit today is one a poller synthesises by diffing two
snapshots — announcing a transition it did not witness and cannot time.
That is the fabrication class the whole core port spent seven seams
killing. The plugins seam therefore ships NO event type by COO ruling, and
marks the three unreachable readings in its own definition
(`jinn_plugins::UNREACHABLE_AT_PIN`) behind a canary check that refuses any
catalog answer delivering one. **That canary is the tripwire this card is
meant to trip:** when the publish path lands, it must go red, and the
harness must then be able to retire the marking on evidence rather than on
belief.

**What it unblocks, stated so the scope stays honest.** The operator has
set a direction where the web UI is a renderer of the plugin tree and a
user extension is a listener on the bus. If extensions are listeners, the
event surface IS the extension surface. This card is the spine of that, and
that is the reason it moved from a backlog nicety to the next kernel
packet — but nothing about the UI is in scope here, and no UI concern may
widen this card.

## Scope

**Kernel-published typed events on the existing bus, for the transitions
the kernel already commits.** The `FiberTransition` it writes to the ledger,
delivered to listeners holding a `jinn:introspect` grant, under the same
attribution the ledger row carries. The kernel already has the value, the
bus, the attribution and the grant check; what is missing is the publish.
With it, a catalog emits what it WITNESSED rather than what it inferred.

Additive per R12: a new event topic on the `jinn:plugin` world's `events`
interface and its declaration in `contracts/jinn-introspect`. No existing
contract changes shape.

**Authority must be PROVEN, not widened — the M2-K8 lesson.** A delivered
transition must reveal nothing about a fiber that the holder's
`jinn:introspect` grant does not already let it pull. That argument is
plausible, and plausible-and-wrong is exactly what the M2-K8 bind-range
hull was after it was pre-blessed and the verifier proved it admitted an
ungranted port. So it is acceptance, not preamble: demonstrate it, and if
the demonstration fails, the delivery gets its own grant.

**Three design questions the round must settle on evidence, not taste:**

1. **Ordering against the ledger.** A listener must never see a transition
   the ledger does not yet carry. Decide the ordering, state it in the
   contract, and prove it — a reader that can observe an event whose ledger
   row is not yet committed breaks Law 2's "model-visible means logged" at
   the moment it matters most.
2. **Back-pressure.** A slow or failing listener must NOT stall, reorder or
   drop a transition silently. A lifecycle publish a plugin can back-pressure
   is a new deadlock surface, and this kernel already carries one unretired
   (#4/#32). Whatever the answer is — bounded queue, drop-with-a-count,
   detach-the-listener — it is typed, ledgered, and observable. A drop that
   is not counted is the absence class returning.
3. **Late join and replay.** A listener that mounts mid-life either gets a
   defined replay window or is told plainly that it missed things. "It just
   starts receiving" is not an answer; it is the absence class wearing a
   different hat.

## Acceptance

- The event declared additively per R12 in `wit/plugin.wit` and
  `contracts/jinn-introspect`, with no existing contract changing shape.
- A fixture through the REAL daemon where a listener holding
  `jinn:introspect` receives the transitions the kernel commits, in an
  order that never precedes their ledger commit, RED-FIRST.
- Red-first proof that a slow or failing listener cannot stall, reorder or
  silently drop a transition; whatever the chosen policy is, its effect is
  typed and its drops are counted.
- Late-join / replay semantics decided, stated in the contract, and tested.
- The authority demonstration — a delivered transition reveals nothing an
  existing `jinn:introspect` grant does not already admit — with its result
  stated EITHER WAY, and its own grant added if it fails.
- Harness FINDINGS #40 and #41 both answerable by evidence after this
  lands. **The harness's `no-transient-reading-at-this-pin` canary going
  red against the new kernel is the point of the card, not a regression** —
  say so in the packet report, because the next reader will otherwise treat
  it as a break.
- Ratchet no regressions; gates / loom / miri / `--locked` green; two-key
  clean; contract deltas additive per R12.

## Out of scope

- Anything in the harness. This card changes the kernel only; the harness
  adopts it in a later pin bump, and the marking in `jinn_plugins` is
  retired there, on evidence, not here.
- Retiring the nested-dispatch deadlock (#4/#32). It is the reason the
  whole stack polls and it is real, but it is a separate and much larger
  card. If this packet's back-pressure answer turns out to depend on it,
  that is a finding and an escalation — not a quiet widening.
- Any UI, extension-authoring or JS-tier concern. The direction that makes
  this card urgent is not licence to build toward it here.
