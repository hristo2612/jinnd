## The defect

SOURCE-OF-TRUTH §3 promises two things of Services and one of Epoch gating:
*a fiber activates only when every injected service's provider is Active*;
*availability is managed reactively by the kernel, never polled by plugins*;
*any provider change forces consumers through a full clean unload → reload.
There is no silent replace, ever.* The kernel delivers all three on the typed
lane (`jinnd-registry`: `Injection` → `InjectedReadiness` → the fiber's
`ReadinessSignal`; consumers' epochs carry every provider's generation). It
delivers none of them on the R3 string lane — `services.resolve` /
`services.call` over the broker — which is the only lane a Tier A wasm plugin
has (R7: Tier A is the only live tier), so in production it is THE lane.
The wasm lane registers with `injects: Vec::new()`
(`crates/jinnd-wasm/src/lane/spawn.rs`), so every wasm fiber's readiness epoch
is the empty vector: always ready, gated on nothing.

Harness FINDINGS #7 named this at the first production consumer (sibling
activation order is UNSPECIFIED). Harness packet UI-1 (PLA-349) then hit it in
a shape that cannot be worked around inside the plugin, at pin `85d36b4`,
four boots out of five. The UI-1 card requires the transport
(`jinn-api-http`) to read the UI bundle ONCE, at `activate`, as an injected
dependency of a sibling's contract (`jinn:ui-bundle`) — the only shape under
which a byte served to a browser is never a crossing on an unauthenticated
connection's behalf. `services.resolve` answers a handle from the GRANT
alone, so the resolve succeeds before any provider exists; the first CALL is
what meets the provider. One boot of the `ui` profile (harness
`tests/composition/tests/ui.rs`, proof 3), FINDINGS #45 verbatim:

```
seq entry           kind
 20 jinn-api-http   ContractResolved { contract: "jinn:ui-bundle" }
 27 jinn-api-http   ContractCall { contract: "jinn:ui-bundle", operation: "manifest" }   → missing-dependency
 44 jinn-ui-bundle  ServiceProvided { service: "jinn:ui-bundle" }
 69 jinn-api-http   FiberTransition { from: "Pending",   to: "Loading",   cause: "InitialLoad" }
 70 jinn-api-http   FiberTransition { from: "Loading",   to: "Unloading", cause: "InitialLoad" }
 71 jinn-api-http   FiberTransition { from: "Unloading", to: "Failed",    cause: "InitialLoad" }
 75 jinn-ui-bundle  FiberTransition { from: "Pending",   to: "Loading",   cause: "InitialLoad" }
 76 jinn-ui-bundle  FiberTransition { from: "Loading",   to: "Active",    cause: "InitialLoad" }
```

The transport failed at 71 for want of a provider that reached Active at 76,
and rested `Failed` for the daemon's life. The environment moved and nothing
re-armed it, because the typed lane's epoch gating does not see a resolve
made on the string lane. The same boot, ordered the other way, is a working
transport — which is exactly why this is a defect and not a style note. The
independent verifier reproduced the coin toss by hand: transport `Failed`,
bundle `Active`, port never listened; second boot fine.

**The provider's own announcement cannot repair it.** The first fix tried
was the obvious one — the provider emits a topic once it has provided and a
transport whose activation found no provider completes its read on that
event — and the kernel refused it in its own words (#45, verbatim):

```
 41 jinn-api-http   EffectRegistered { label: "listen jinn:ui-bundle/provided" }
 44 jinn-ui-bundle  ServiceProvided { service: "jinn:ui-bundle" }
 47 jinn-api-http   CycleRefused { on: "jinn:ui-bundle.manifest", target: 11, target_entry: "jinn-ui-bundle", through: [3] }
 51 jinn-ui-bundle  DispatchTrace { topic: "jinn:ui-bundle/provided", mode: Emit, listeners: 1, failures: 1, emitter: 11 }
```

A listener that calls back into the entry whose emit is awaiting it is the
wait cycle M2-K10 refuses whole — and the emit lands while the provider is
still `Loading`, before the provision is callable at all. That refusal is
correct and stays. What it proves is that readiness is the KERNEL's fact to
publish, not a provider's to announce (§3: never polled by plugins).

**The other half — replacement (#46, proof 4, every run).** With the
transport holding a `jinn:ui-bundle` handle it resolved at activation, the
operator edits the bundle entry's `package` and `hash`:

```
proof 4: swap served 1.240117s after the edit; refused connects while it
landed: 0; transport incarnation 4 -> 4; bundle crossings 1 -> 2
```

The bundle entry restarted (its artifact changed); the transport did not — no
transition, no incarnation, no listener blip. Its resolved handle is not a
lease the kernel gates on, so the kernel had nothing to say to it. What
served the new document 1.24 s later is the harness's own workaround.

**The workaround, and its cost.** UI-1 ships the only kernel-free
completion available: the transport subscribes to
`jinn:introspect/transitions` under a `jinn:introspect` grant the profile
gives it for no other purpose, probes the manifest once more after
subscribing so an Active transition cannot fall between probe and
subscription, and reads when it WITNESSES its bundle entry reach Active
(proofs 3–5). It costs a read-only kernel contract on the transport's grant
list, up to two extra `manifest` crossings per boot, and a delivery to the
transport for every fiber transition anywhere in the composition, for the
daemon's life. Every activation-time injection in the distribution would
need the same code. That is a plugin polling the kernel's lifecycle by
another name.

## North-star fit

§1: *a product is a profile (a named plugin tree), not a codebase.* A
profile whose boot is a coin toss does not describe a running system; it
describes two, and the operator learns which one they got from the port.
§3 promises reactive availability and epoch gating for the paradigm, not for
one lane of it. I4 (confluence): a `Failed` that depends on the order two
siblings happened to load is a history trace the quiescent state is supposed
to be free of. I3 (progress): an entry that would have activated had it
waited is not "cleanly inactive", it is wrongly dead. R9 forbids retrying
against an unchanged environment; the 2026-08-25 ruling 2 ("Failed-fiber
re-arm dated") already answers the other direction on the typed lane —
re-arm when the aim changes — and the provider landing IS the change. The
kernel has all the machinery; this card carries the declaration to the lane
that lacks it.

## The contract delta

**One additive, optional list per wasm entry: `injects`, beside `grants` in
the entry's `config` document** — the place the daemon's seat decoder
already reads (`crates/jinnd-daemon/src/seat.rs`: `config.grants`,
`config.data`). Each element names a string-lane contract exactly as a grant
does (`"jinn:ui-bundle"`, or `{ "contract": "jinn:ui-bundle" }`; no scope —
scope is authority, and this list carries none). Declaration order is part
of the epoch's identity, as on the typed lane.

```json
{
  "id": "jinn-api-http",
  "package": "…", "version": "…", "hash": "…",
  "config": {
    "grants":  ["jinn:net", "jinn:auth", "jinn:ui-bundle"],
    "injects": ["jinn:ui-bundle"],
    "data": "…"
  }
}
```

**What a declaration means — the typed lane's `injects` semantics, verbatim
on the string lane:**

- **(a) Activate only once every declared provider is Active.** The entry's
  fiber rests `Pending` until, for every declared contract, a provision is
  live on the broker AND the providing fiber is `Active` (a `ServiceProvided`
  row lands during the provider's `activate`, while it is still `Loading` —
  #45 seq 44 vs 76 — so provision alone is not readiness). The fiber's
  readiness epoch is the vector of (provider fiber, provider generation) per
  declared contract, in declaration order; `None` while any is missing.
  Epoch identity is by value: a provider that flickers away and back to the
  same identity coalesces to no consumer work (the registry's existing
  rule). In the #45 boot the transport would rest `Pending` through seq 76
  and then load: no `Failed`, no probe, no second `manifest` crossing.
- **(b) Unload → reload when a declared provider is replaced (§3 epoch
  gating, R9).** A provider change — its entry's artifact swap, config
  restart, reconcile, or its own failure and re-arm — bumps the broker
  generation the declaration watches; the consumer's epoch changes; the
  fiber engine plans the reload it already knows how to plan: the consumer
  goes `Active → Unloading → Pending → Loading → Active`, recorded with
  `TransitionCause::DependencyChanged`, incarnation +1, siblings untouched
  (I1, R11). A provider WITHDRAWN with no successor takes the epoch to
  `None`: the consumer unloads to `Pending` and waits. Never a silent
  replace, never a retargeted handle — the broker's generation-pinned handle
  keeps refusing a stale call typed, exactly as today.
- **(c) Re-arm rather than rest `Failed` when a declared provider lands
  later — and only then.** Consistent with ruling 2 (2026-08-25): a failed
  activation is retried against a CHANGED environment and against nothing
  else. With (a) in force the #45 ordering can no longer produce a `Failed`;
  (c) covers the consumer that activated against a live provider and failed
  on its own account (UI-1 proof 5: a bundle whose bytes do not match its
  manifest). When the operator repairs the provider by profile edit, the
  provider's generation moves, the consumer's epoch moves, and the fiber
  engine re-arms it: `Failed → Pending → Loading → Active`,
  `DependencyChanged`, on the record. While nothing declared has moved, the
  consumer rests `Failed` exactly as today (R9). A provider withdrawn
  without replacement re-arms nothing.

**Grants and declarations are different facts.** A declaration gates; a
grant authorizes (constitution 01: requests are not grants). A declared
contract the entry holds no grant for is a per-entry fault refused ON THE
RECORD at the seat's existing fail-closed admission point (R11): the entry
loads nothing and its siblings load normally. A declaration never widens
what the entry may call. A declared kernel-supplied contract (`jinn:fs`,
`jinn:clock`, …) is admitted and is trivially ready — the kernel's own
providers hold a fixed generation — so an author may declare everything
they inject without knowing which contracts are kernel-owned.

**What an UNDECLARED resolve still does: exactly what it does today.** An
entry with no `injects` list has the empty epoch it has now: it activates
whenever its own entry loads, `services.resolve` answers from the grant
alone, the first call meets the provider or gets `missing-dependency`, a
provider swap leaves it untouched, and a failed activation rests `Failed`.
No existing profile changes behaviour by one ledger row. The declaration is
opt-in per entry; the gate exists only where an author asked for it.

**Loader and document: no change.** `injects` rides inside `config`, which
the loader carries as an opaque value and the facade types as `C`; the
document decoder, `DocumentEntry`, write-back, and `extra` are untouched. An
edit to an entry's `injects` is a config edit and restarts that entry by
reconcile (constitution 04), which is correct: what an entry injects is an
epoch input.

**The ONE design decision in scope — the readiness source.** The wasm lane
today gates on the loader-supplied `WatchReadiness` (empty injection). The
implementer decides how the declaration becomes a `ReadinessSignal` whose
epoch is the broker's provider generations: the recommended shape is a
broker-backed signal (provider table + fiber-state watch → `Option<Epoch>`
on the store's change edge, published only when the epoch moved) fed into
the same fiber signal the lane already hands to `track`, so `jinnd-fiber`
is not touched and the supervisor's existing `DependencyChanged` planning
does (b) and (c) unaided. If the fiber engine must change, this card's
"no loom" note is void and a loom model is owed (AGENTS.md). Rejected
shapes: mirroring string-lane provisions into the typed registry (two
registries for one fact, R10), and a per-consumer poll (§3).

## Profile-schema delta

Additive: one optional `injects` list per wasm entry, in `config`, beside
`grants`; absent means the empty list. A malformed element (not a string,
an object naming no `contract`, a scope or ops key) is a per-entry fault
refused on the record like a malformed grant (R11, fail closed). The seat
config is the wasm entry's contract-level config document; this is a 0.x
MINOR of that schema per R12 — nothing existing profiles carry is reread
differently. Constitution `docs/constitution/04-profiles.md` §Format gains
the field and one sentence under §Reconcile semantics stating that a
string-lane declaration is an epoch input exactly as a typed injection is.

**Contract delta, additive (R12):** `jinn:introspect` 0.5.0 → 0.6.0 — an
entry read carries its declared `injects` and, while the fiber rests
`Pending` on the gate, which declared contracts are unmet, so an operator
can see WHY an entry has not activated (Law 2, and the K9/K10 precedent
that a refusal is observable, not inferred). Exact field names are the
implementer's, declared in round 1; the contract-lens gate (M2-K16/K22)
governs the bump. No change to `wit/plugin.wit` — `services.resolve`,
`services.call`, and every error case stay as they are.

## Facade delta

**None.** No `jinnd-api` item is authorized. The declaration is inside the
opaque config the facade already carries; `TransitionCause::DependencyChanged`
already exists; the ledger vocabulary already has `ServiceProvided` /
`ServiceWithdrawn` / `FiberTransition`. If the implementer finds a facade
item necessary, STOP and escalate with the item named (the M2-K20 rule); an
unauthorized facade item is an automatic blocker (two-key).

## Invariant cases the verifier will own (named here, written by the verifier)

Homes are the verifier's call: what the facade can drive belongs under
`tests/invariants/`; what needs the real daemon and two wasm guests is named
here so the verifier's fixture can be built once. Both boot orders must be
FORCED, never waited for — the #45 coin toss is the fixture's own control.

1. `a_declared_consumer_rests_pending_until_every_declared_provider_is_active`
   — provider-first and consumer-first orderings; on the record: no
   `Failed`, no `missing-dependency`, exactly one consumer activation, and
   the consumer's `Active` row after the provider's.
2. `replacing_a_declared_provider_reloads_its_consumer_exactly_once_and_no_sibling`
   — the #46 shape: one `DependencyChanged` unload → reload on the
   consumer, incarnation +1, an undeclared sibling's incarnation unchanged
   (I1, R11), and a consumer call on the old handle during its own teardown
   refused typed, never retargeted (R9).
3. `a_failed_consumer_re_arms_when_a_declared_provider_moves_and_never_before`
   — ruling 2 on the string lane: `Failed` stays `Failed` across an
   unrelated sibling's restart and across a provider flicker to the same
   identity; a provider generation change re-arms it once, on the record.
4. `a_provider_withdrawn_without_successor_parks_its_consumer_pending`
   — the epoch goes to `None`; the consumer unloads cleanly and waits; a
   later provision reactivates it (I3: no deadlock, quiescence reached).
5. `an_undeclared_entry_is_unchanged_by_this_packet` — the ratchet: a
   profile with no `injects` produces the same transitions and the same
   `missing-dependency` on first call as at `d7440e2`.
6. `a_declaration_without_a_grant_is_a_contained_entry_fault` — refused on
   the record, siblings Active, nothing widened (R11, constitution 01).
7. `mutually_declared_entries_rest_pending_and_say_so` — the recorded
   limit (see §Out): both rest `Pending`, neither `Failed`, both visible on
   `jinn:introspect` naming the unmet contract (I3: cleanly inactive).

## Harness consequence, and the pin-bump that adopts it

- UI-1's `jinn:introspect/transitions` subscription in `jinn-api-http`
  becomes dead code and is removed, with the `jinn:introspect` grant the
  `ui` profile gave the transport for it; the transport's entry gains
  `"injects": ["jinn:ui-bundle"]`.
- Proof 3: `manifest` crossings tighten from `1..=3` to exactly 1.
- Proof 4 flips: transport incarnation +1 (`DependencyChanged`), one
  `bundle` crossing per incarnation, and the "refused connects" figure
  becomes the ~30 ms reconcile blip the UI-1 card predicted, asserted as a
  bound — no longer 0 with #46 as the reason.
- Proof 5 collapses to one order: the transport never activates before the
  bundle, so a corrupt bundle always fails the transport's ACTIVATION (port
  never opens) and the "delivery" branch is removed. Repairing the bundle
  by profile edit then re-arms the transport without an operator restart
  (c) — a new assertion the verifier may add.
- Adopted by **harness pin-bump 7** (the next after pin-bump 6 = PLA-344 at
  `85d36b4`): it bumps the daemon pin and the `jinn:introspect` pin, makes
  the three edits above, and closes FINDINGS #7, #45 and #46 with the pin's
  sha in the FINDINGS entries, the standing form.

## Explicitly OUT

- **No cycle resolution beyond what M2-K10 refuses today.** Dispatch-time
  wait cycles keep their typed `cycle-refused`; this card neither queues nor
  defers a cycling call.
- **No static cycle chart on the string lane.** A wasm entry declares what
  it injects, not what it provides (provision is a runtime `provide` call),
  so the loader's typed-lane chart cannot see string-lane edges. Two entries
  that declare each other rest `Pending` forever, visible on introspect
  (case 7) — I3's "cleanly inactive", detected by an operator reading the
  record rather than statically. Recorded as a named limit; a `provides`
  declaration is a later card if a consumer needs it.
- **No I2 lease semantics on the string lane.** A dying provider does not
  wait for its declared consumers' teardown; the generation-pinned handle
  keeps refusing typed. Ordering between a replaced provider and its
  reloading consumer is as today. A later card if a consumer needs it.
- **No soft, optional, or timed dependency.** A declaration is hard; there
  is no "activate anyway after N seconds" (R9: no retry against an unchanged
  environment, and no polling in disguise).
- **No change to typed-lane entries, `wit/plugin.wit`, `services.*`, the
  loader document schema, `jinnd-api`, or the fiber engine** (intent; see
  the ONE design decision).
- **No harness-side change in this packet.** Pin-bump 7 is its own packet.
