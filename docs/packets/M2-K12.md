# M2-K12 — CI is green on Linux, and the keystore's authority property holds there

**Milestone:** M2 (defect-in-the-open; found 2026-08-30 when Hristo asked why CI
showed 2/6 gates passing) · **Owner:** kernel-dev · **Status:** ready ·
**Binding rules:** R1, R3, R5, R9, R10, R11, R12, Laws 1/2/4 · **LOC ceiling
(card-authoritative; canonical meter = the M2-K3 numstat form over the surfaces
this card names, with R10's exclusion list applying in full — this card does not
restate it and never narrows it):** combined production net delta ≤400 across
`crates/jinnd-wasm/src`, `crates/jinnd-daemon/src`, `.github/workflows` ·
facade delta ≤20 · **Standing gates:** all usual + `cargo build --workspace
--locked`, and a GREEN CI RUN ON MAIN quoted by run id.

**THREAT MODEL (stated before round 1, per the standing law):** the kernel
running on a platform WITHOUT a system keychain, under ordinary operation. NOT an
attacker holding both the data root and the passphrase. The property under test
is that the data root ALONE cannot decrypt the store — and that must hold on
every platform, not only the one we develop on.

**STOP RULE (stated before round 1):** at most 4 rounds, then anything open that
is not a self-contradiction or an outright false statement becomes a named known
limit and the packet lands — **EXCEPT the authority property itself**, which is a
Law 4 obligation and may NOT land as a known limit. If it cannot be made to hold
on Linux, that escalates to Hristo as an architecture decision.

## Why, and what was already fixed

CI was red on EVERY jinnd commit from 2026-08-27 to 2026-08-30, including
docs-only ones — the signature of a build-configuration break rather than a
defect in any diff. `8d58501` (M2-K8 round 2) introduced the macOS keychain
target block for `security-framework` and captured the existing `wasmtime` line
inside it. `wasmtime` is this crate's core runtime on every platform, so Linux
resolved without it. Fixed by the COO in `da4cf9a` (build config only, proven
from cargo's resolved metadata, `Cargo.lock` byte-unchanged). That turned `loom`
green and got `fmt` and `clippy` green in `gates`.

**What that compile error was hiding is this packet.** With the build repaired,
two keystore tests RAN on Linux for the first time and FAILED:

- `crates/jinnd-daemon/tests/keystore/authority.rs:90` —
  `authority::the_data_root_alone_cannot_decrypt_the_store`, on the assertion
  **"a different passphrase does not open the store"**. A deliberately WRONG
  passphrase returns `Ok` on Linux.
- `crates/jinnd-daemon/tests/keystore/journal.rs:48` —
  `journal::an_fs_effect_and_a_keystore_effect_sharing_an_id_both_survive_suspension`.

Local macOS gates were green throughout, every packet reported them honestly, and
the property still did not hold. That is the whole argument for CI mattering.

## Scope

1. **Establish the mechanism BEFORE changing anything, with a transcript.**
   `MasterKeySource::resolve`'s `Passphrase` arm is platform-symmetric
   (`derive(passphrase, dir)` on both), so the divergence is elsewhere. Candidates
   include salt creation/read on first open, whether the store is populated at all
   on Linux so a wrong key has ciphertext to fail against, and whether the test's
   own setup assumes a keychain. A wrong-passphrase open that succeeds because the
   store is EMPTY and one that succeeds because the key is not gating decryption
   are different defects with different fixes. Say which it was.
2. **Make the property hold on Linux** and prove it there.
3. **The `invariants` job** fails separately on `tests/invariants/cordis_handles.rs:44`
   (`extended_service_handle_keeps_dependency_snapshot`) with an accompanying build
   failure. Diagnose on its own evidence; do not assume it is the same family. If it
   is an expected-red V02_DEFERRED case the ratchet should tolerate, say so and fix
   the ratchet's Linux behaviour instead.
4. **A regression guard**, so a platform-only dependency or a platform-only
   property cannot silently return. At minimum the kernel pipeline's land step
   asserts post-merge CI green on main and blocks on red — the asymmetry that let
   this live for three days is that the harness pipeline does this and the kernel
   pipeline does not.

   **SCOPE OF THE GUARD, narrowed by COO ruling 2026-08-31 round 3 (see below).**
   The guard's guarantee is TEST PARITY: a test compiled in on one platform and
   absent on the other, or live on one and silenced on the other, is refused. It
   does NOT and cannot cover a test that COMPILES AND RUNS on both platforms but
   whose body returns early — via `env::consts::OS` or anything else — because
   such a test has an identical name and identical state in both inventories.
   That is a VACUITY defect, not a platform-gating one, and it has a different
   remedy (see the ruling).

## Do NOT weaken the tests to pass

`#[cfg(target_os = "macos")]` on a failing security-property test is the forbidden
move: it converts an unverified property into an invisible one. If the property
genuinely requires a platform key store, the Linux path is
passphrase-derived-outside-the-data-root — which the design already names — and
that path is implemented and proven, not skipped.

## Acceptance

- CI green on Linux for every job on a push to main, **verified by an actual green
  run on the pushed head and quoted by run id** — never by local gates.
- The mechanism established with a transcript before the fix, stated in the report.
- Both keystore tests pass on Linux on their merits: no test gated to macOS, no
  assertion weakened.
- The `invariants` failure fixed at its real cause.
- The regression guard in place.
- Ratchet no regressions; gates/loom/miri/`--locked`; two-key clean; ceilings per
  this card; contract deltas additive per R12.

## Out of scope
Any change to the keystore's cryptography or key-derivation choices; the macOS
keychain path, which works; harness-side changes.


## COO RULING — round 3 escalation, 2026-08-31

The verifier escalated rather than reworking, correctly: my round-3 ruling
asserted that a name/state differential catches a body using `env::consts::OS`
with an early return. **It does not, and I withdraw that claim.** Such a test is
present, compiled and green in BOTH inventories; nothing in a name-set comparison
can distinguish it. The implementer's script said so in its own header and the
verifier proved the shipped fixture only demonstrates name DELETION. The
acceptance as I first wrote it demanded something the mechanism I mandated cannot
do — a self-contradiction, and mine.

**Ruling: NARROW THE GUARANTEE AND NAME THE LIMIT, because these are two defect
classes, not one.**

- A test that **VANISHES or is SILENCED** on a platform is a platform-gating
  defect. The differential catches it, including cases no scanner could — an
  entire test binary disappearing with no `cfg` syntax anywhere. That is real and
  it stands.
- A test that **RUNS AND DOES NOTHING** is a VACUITY defect. It is the same class
  as this packet's own founding finding: the keystore assertion was correct,
  compiled, executed, and passing over an empty store. No inventory, scanner, or
  name comparison can see vacuity. Its remedy is the NON-VACUOUS PRECONDITION
  discipline this packet already established in
  `crates/jinnd-daemon/tests/keystore/authority.rs` — a test states and asserts
  the precondition that makes its main assertion meaningful.

Narrowing here is not weakening a boundary; it is deleting a claim that was never
satisfied and replacing it with one that is enforced. An acceptance nobody can
meet is worth less than a smaller one that holds.

**Required in round 4, and nothing else:** state this limit in
`.github/scripts/test-inventory.sh`'s own header and in the differential's output
line, in the same honest register the demoted heuristic already uses; relabel the
`test-check-test-inventory.sh:122` fixture to say what it actually proves (name
deletion), not what it does not.

**Explicitly NOT built here:** the verifier's second option, a per-property
execution witness proving a body reached its meaningful assertion. It is the real
answer to vacuity at scale and it is a genuine proposal — but it is a new
mechanism across every test, far outside this card and R10's "small and boring".
It becomes its own card on this evidence if we want it.
