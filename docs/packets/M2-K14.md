# M2-K14 — `jinn:net.request` exists as a declared hole: no outbound call is possible at any pin, and the authority to make one has never been built

**Milestone:** M2/M3-entry (roadmap §7 M3 blocker, named 2026-09-01) ·
**Owner:** kernel-dev · **Status:** round 2 · **Binding rules:** R1, R3, R5,
R9, R10, R11, R12, Laws 1/2/3 · **Design decisions in scope: ONE** — how an
outbound call is authorized, declared and ledgered · facade delta ≤45
(amended from ≤30, COO 2026-09-01 — see the facade note below) ·
**Standing gates:** all usual + `cargo build --workspace --locked`.

**SCOPE IS DELIBERATELY SPLIT — read this before anything else.** This card
builds the AUTHORITY and IRREVERSIBILITY machinery for an outbound call and
proves it against a loopback HTTP target. **TLS and real internet hosts are
NOT in this card**; they are M2-K15, and that card will carry exactly one
design decision (which TLS stack, justified under R10) because this one
will already have settled how an outbound call is authorized, declared and
ledgered. M2-K13 was scoped as three design decisions in one packet, its
ceiling was wrong twice, and it took four rounds. That lesson is why this
is two cards.

**THREAT MODEL (stated before round 1, per the standing law):** an honest
plugin that is granted outbound access to some hosts and must not reach
others, and an honest plugin whose request carries a credential that must
not land in the ledger. NOT a malicious plugin with arbitrary code
execution attempting to exfiltrate through a granted host — a plugin that
holds a grant to a host can send that host whatever it likes, and narrowing
that is a profile-authoring concern, not a kernel one. Defects reachable
only that way are named known limits.

**STOP RULE (stated before round 1):** at most 4 rounds. After that,
anything open that is not a self-contradiction or an outright false
statement becomes a named known limit and the packet lands.

## Why

`contracts/jinn-net/contract.wit` has declared `request` since M2-K6 and
has never provided it: *"the outbound one-shot (NOT PROVIDED in v0.1 — no
HTTP client in the kernel, R10; answered as a typed failure)"*. So the
surface is honest — it refuses rather than lying — but the consequence is
total. **No plugin at any pin can reach anything off this machine.** Slack,
Stripe, Linear, GitHub, every vendor engine API and every webhook are
structurally impossible in the harness today.

That is recorded in §7 as one of two blockers making M3's acceptance —
*"an instance runs a full day on jinnd alone"* — unreachable as written: an
instance that can reach nothing is not running the business. The harness's
own README says the same from the other side, and the web-UI inventory
found it again independently.

## The spine: this is the kernel's first genuinely irreversible effect

Law 3 admits exactly two categories and constitution `03-revert.md` is
explicit: an operation is `revertible` with a defined inverse, or it **must
be declared `irreversible`** — *"there is no third category"*, and *"an
undeclared irreversible effect discovered in review is a Law 3 violation,
not a bug."*

**A sent request cannot be un-sent.** Every effect the kernel has shipped
so far has had an inverse — even `jinn:fs` write moved from irreversible to
revertible in 0.2.0 once it had a trash. This one never can. So:

- `request` is declared `effect = "irreversible"` in
  `contracts/jinn-net/metadata.toml`.
- A revert unit containing a `request` event is **REJECTED**, per
  `03-revert.md` §51 and the machinery already in
  `crates/jinnd-ledger/src/revert.rs`. Prove the rejection RED-FIRST — a
  revert that silently skips an irreversible event, or that succeeds while
  pretending the call did not happen, is the falsehood this whole program
  exists to prevent.
- The refusal names WHAT it could not revert and WHY, typed. "Revert
  failed" is not an answer.

## Authority: the outbound allowlist is acceptance, not preamble

The contract already says `request` is *"authorized against the scope's
outbound host allowlist by the edition that provides it."* Build that, and
prove it the way M2-K8 taught us — that packet's bind-range hull was
plausible, pre-blessed by the COO, and the verifier proved it admitted an
ungranted port.

- A request to a host NOT on the scope's allowlist REFUSES, typed,
  distinguishable from a network failure and from a malformed URL. Three
  different readings, three different answers, never one blurred one.
- The allowlist is authored in the profile and readable by nobody's
  courtesy — a plugin cannot widen its own. Prove it, do not assert it.
- Redirects: a 30x to an off-allowlist host is an off-allowlist request and
  must be refused, not followed. This is the obvious hole and it must be
  closed here or named as a limit with a reason.

## Law 2 vs secrets: what a request writes to the ledger

Model-visible means logged — but a request body or an `Authorization`
header may carry exactly the credential the keystore exists to protect.
Decide and state the record: method, host, path, status, byte counts and
duration are the shape this card expects; **never the body, never
credential-bearing headers**. If the decision differs, say why in the
packet report. A ledger row that leaks a secret is worse than no row, and a
row that omits everything is not a record.

## R1: non-blocking

`request` returns a result but must not block the kernel or hold a lock
across a plugin-facing call. Decide the shape, state it, and prove no
`block_on` reaches kernel code. A one-shot that stalls the runtime while
the network is slow rebuilds the head-of-line problem M2-K13 spent three
rounds removing.

## Acceptance

- `request` provided for plain HTTP against a LOOPBACK target only,
  declared additively per R12; TLS and non-loopback hosts explicitly out of
  scope and named as such in the contract.
- `effect = "irreversible"` declared in `contracts/jinn-net/metadata.toml`,
  and a revert unit containing a `request` event REJECTED with a typed
  refusal naming what it could not revert — proven RED-FIRST.
- Allowlist enforcement proven through the REAL daemon: an allowed host
  succeeds, an off-allowlist host refuses, a redirect to an off-allowlist
  host refuses, and a malformed URL is a third distinct answer. Each
  asserting its own precondition — a refusal test that would pass with the
  allowlist empty proves nothing.
- The demonstration that a plugin cannot widen its own allowlist, with its
  result stated EITHER WAY.
- The ledger record shaped as above, with a test proving a credential-
  bearing header does NOT appear in the row.
- No `block_on` in kernel code; no lock held across the call.
- Ratchet no regressions; gates/loom/miri/`--locked` green; two-key clean.

## Out of scope

- **TLS and real hosts — M2-K15.** Do not add a TLS dependency here. If the
  authority model turns out to be undecidable without knowing the TLS
  shape, that is a finding and an escalation, not a widening.
- Retrying, connection pooling, streaming bodies, or anything resembling an
  HTTP client library's comfort features. R10: small and boring.
- Auth on the kernel's own inbound surface. That is the OTHER M3 blocker
  and it is a separate card with a design decision Hristo owns.
