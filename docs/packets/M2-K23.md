## The gap

**By code at pin `655f07e`.** The kernel has exactly one runtime-led
write to the document of record that a plugin can reach:
`jinn:profile.patch-entry` (`contracts/jinn-profile`, 0.2.0; M2-K7/K8),
which merges an RFC 7396 patch onto ONE entry's `config` subtree and
hands the loader a `Loader::update_entry_deferred` — validated, written
back atomically, restarted by reconcile-by-id, recorded as
`ProfilePatched { entry, by }`. `package`, `version`, `hash`, `disabled`
and `parent` are siblings of `config`
(`crates/jinnd-loader/src/document.rs`, `DocumentEntry`), so through the
surface a person or an agent actually uses an operator can change what a
plugin is CONFIGURED with and never what a plugin IS, whether it is
present, or whether it runs. The loader's document-led reconcile already
knows every one of those moves — `diff.rs` plans `Create`, `Track`,
`Enable`, `Disable`, `Remove`, `Replace`, `Restate`, `Rebind` — but the
only way to reach them is to edit the file behind the daemon and wait for
the watcher. Every seam proof in the harness does exactly that
(`Daemon::edit_profile_restarting`), and FINDINGS #37 has the transcript:

```
FINDINGS #37 transcript — PATCH /v1/profile/entries/jinn-plugins-appliance {"package": "plugins/jinn-plugins-profile"}
HTTP/1.1 200 OK
{"api-version":"0.3.0","changed":false,"entry":{ ... ,"id":"jinn-plugins-appliance",
 "package":"plugins/jinn-plugins-static","hash":"c8200f5...","parent":null,"version":""}}
  (then, as the precondition, on the same entry through the same route:)
  PATCH {"config": {"data": {"ledger-limit": 64}}}  ->  200, changed: true,
  entry.config.data.ledger-limit == 64, entry.package == "plugins/jinn-plugins-static"
```

Constitution 04 §Write-back is confined names the capability this card
supplies, verbatim: *"Grants, identity, nesting, isolation, interception,
policy, and profile ancestry require a separate operator-authorized
control capability (`jinn:profile-admin`); every write-back is a ledger
event."* No such contract exists at any pin. The UI malleability arc
(harness `docs/plans/ui-malleability-arc.md`, KG-1) names it in every
phase from UI-2 on; UI-7's enable/disable is blocked on it; the plugins
page renders five disabled pills for it (`web/src/routes/settings/plugins/not-yet.tsx`:
install, remove, disable, widen topics, swap engine — each "Waits on
jinnd M2-K23"); "install an extension from the UI" is a file edit until
it lands, and the UI-2 card says so.

**A second fact, found by this card's reading, and worse than the gap.**
`patch-entry`'s validator (`crates/jinnd-daemon/src/daemon/profile_cap/patch.rs`,
`validate`) checks that the patched config is an object whose `grants`
WOULD ADMIT at activation. It does not check that `grants` is UNCHANGED.
`config.grants` is inside `config` — the very subtree `patch-entry`
writes — so a plugin holding `jinn:profile` scoped to entry X can today
patch `{ "config": { "grants": ["jinn:net", …] } }` onto X and the loader
will commit it, restart X, and X will activate with the wider grant. That
is a grants change through the one contract 04 says may never carry one
— a Law-1 side door the constitution's own sentence forbids. This is a
reading of the code at `655f07e`, not a run; the implementer's FIRST red
test is what confirms it (§Round protocol), and if it reproduces it is
closed here (contract delta (d)), not in a later card: the same seam,
the same validator, zero design freedom.

**Whose door this is.** `jinn:auth` (M2-K21) answers "may this connection
issue a dispatch" for the transport that holds the socket, and its card
ruled per-call principal propagation — the door's principal threaded
through the transport's own calls — OUT as delegation between plugins.
So the transport that verified the operator's bearer is, to the kernel,
just a plugin holding grants. What authorizes its `remove-entry` is the
ONE decision of this card.

## North-star fit

§1: the kernel *"can evict anyone without leaving a mark"* — but only an
operator with a text editor can evict anyone at all. Law 4: *"a product is
a profile"* is true of the file and false of every reachable surface. Law
1: our plugins are never special — and today the only thing that can
reshape the composition is not a plugin at all but a process with write
access to the data root. Law 2: a file edit is the ONE composition change
the ledger sees only as its consequences (`WriteBack`, transitions) and
never as an intent with an author. Law 3: a file edit has no recorded
inverse; a kernel write can carry one. R9: a grants widening through
`patch-entry` is a silent authority replacement — the entry restarts
with more than the operator granted and nothing on the record names the
widening. I1/I4: the loader already knows how to remove exactly one
entry's contribution and how to converge on the final document; the
kernel merely refuses to be asked.

## The ONE design decision — what authorizes an admin write

Two shapes, and a third that is not one.

**(i) Per-call principal propagation from `jinn:auth`.** Every admin call
carries the `principal` the transport obtained from `verify`; the broker
threads it through the call; the provider refuses without it. Rejected,
with reasons. (1) M2-K21 ruled delegation between plugins OUT of scope
("if the design starts to resemble an identity system, it has left the
card"), and a per-call principal IS that system's first primitive: a
broker field, a wire field on every `services.call`, a provider check,
and a rule for what a plugin may do with a principal it did not earn.
(2) It proves nothing the grant does not: a transport that holds the
socket can present the operator's credential to `verify` itself and
obtain the principal for any call it likes — the transport is trusted by
the operator's profile or it is not, and the kernel cannot tell the
difference from inside a call. (3) It is not R12-small: a new field on
the world's `services.call` for every contract, to gate one.

**(ii) A separate `jinn:profile-admin` grant on the calling entry —
CHOSEN.** `jinn:profile-admin` is a contract like every other: a
kernel-supplied provider on the string lane, granted per entry in the
profile (scope type `entry-ids`, the same parser as `jinn:profile`; `*`
only when written; `ops` attenuation as M2-K8 defines it), refused at
admission without it, refused at dispatch outside it, every call a
`ContractCall` and every write a row naming the CALLER ENTRY. Whoever
holds the grant is the operator's delegate BY THE OPERATOR'S OWN
DOCUMENT — the profile that grants the transport `jinn:profile-admin`
is the operator saying "this plugin reshapes my composition", exactly as
the profile that grants it `jinn:net` is the operator saying "this plugin
holds my socket". The chain is: operator credential → `jinn:auth.verify`
(the door, proven by harness 2.8) → the transport's own
`jinn:profile-admin` grant (the delegate, proven by the profile) →
the kernel (the record). It is the R12-small answer: one bundle, zero
world changes, the existing scope parser, the existing ops attenuation,
the existing refusal vocabulary.

**The same-uid limit, stated and not papered over.** A process running as
the daemon's own uid can edit the profile file directly, and no grant
holds against it — the same limit `jinn:auth` states in its contract,
its metadata and its code comment. What this capability confines is
PLUGINS: a plugin without the grant cannot reshape the composition, a
plugin with a scoped grant cannot reach outside its scope, and no plugin
can reshape ITSELF or its ancestors (below). What it does not do is
authenticate the operator — that is `jinn:auth`'s and the transport's,
and a transport that issues admin writes for unverified connections is
the harness composition suite's to catch, never the kernel's. The
contract text says all of this in one paragraph (§Contract delta),
asserted by parsing.

**(iii) Not a shape: the file.** "Artifact identity is deliberately out
of every plugin's reach; design seams config-decided" — FINDINGS #37's
cheaper alternative. Rejected because 04 already decided it the other
way, because UI-7 and "install from the UI" are not config-decidable,
and because a law whose only reachable surface is a text editor is a law
for one person.

## The contract delta

`contracts/jinn-profile-admin` 0.1.0, a new bundle: world `admin-provider`,
interface `admin`, reached over `services.resolve("jinn:profile-admin")`
+ `services.call`, wire in the M2-K7 form (u32-LE length-prefixed UTF-8
segments; answer tag `2` accepted + u64-LE ledger sequence, tag `1`
refused + one class byte + the reason's UTF-8). **Five writes, and no
sixth**:

| operation | payload | plan step it applies |
|---|---|---|
| `add-entry` | one entry record — the 0.2.0 `entry` shape: `{ id, package, version, hash, grants, config, disabled, parent }` | `Create` (or `Track` when `disabled`) |
| `remove-entry` | `id` | `Remove` |
| `set-disabled` | `id`, `disabled: bool` | `Disable` / `Enable` |
| `set-grants` | `id`, `grants` as JSON, written as `config.grants` is written | `Restate` (a grants change is an epoch input, 04: the fiber reloads) |
| `swap-plugin` | `id`, `package`, `version`, `hash` | `Replace` — see (e) |

**Every write is an operator INTENT recorded, then applied by
reconcile-by-id — the M2-K7 precedent, runtime-led.** The provider
authorizes (scope + ops, fail-closed), validates the whole result before
anything moves (a malformed record refuses with nothing written), then
hands the loader ONE runtime-led amendment (`Loader::administer`, the
sibling of `update_entry_deferred` and `dispose_entry`): the runtime is
offered the change first — exactly the plan step the document-led diff
would produce for that entry and no other — the document is written back
atomically (stage + fsync + rename, the whole document through
`save_committed`, so preserved raw entries and unknown fields survive),
the daemon treats the write-back as its own echo (M2-K5), and the answer
is `accepted(seq)` once both views committed, the restart or disposal
SCHEDULED and never awaited inside the caller's host call (M2-K8 #26,
R1). Both views at their prior state on any refusal; a failed write-back
withdraws the staged change or records a divergence loud, the `amend.rs`
law.

**(a) One row per write, naming the caller and both digests (Law 2).**
`ProfileAdministered { entry, by, write, before, after, prior }` under
the calling entry's attribution: `write` names which of the five;
`before` and `after` are the SHA-256 hex digests of the RENDERED
document (`Document::render`, byte-for-byte what the loader wrote), so
`after` equals the digest of the file on disk and a reader can check it
with nothing but the file; `prior` is the entry's record BEFORE the
write (the 0.2.0 `entry` JSON) and absent on `add-entry`. `by` is the
caller entry (or `peer:<id>` for a kernel peer, the K7 form). A refused
write is history too: `AmendmentRefused { detail }` under the caller
(K7's kind, the detail naming the class), and a scope or ops refusal is
the broker's own `GrantRefused` with its typed reason. No secret crosses:
the profile carries none (04). Sensitivity class `personal`, as
`jinn:profile`'s reads.

**(b) Every write is reversible under Law 3 where an inverse exists, and
the inverse is ON THE ROW.** The inverse of `add-entry` is
`remove-entry(id)`; of `remove-entry` is `add-entry(prior)`; of
`set-disabled` is `set-disabled(!disabled)`; of `set-grants` is
`set-grants(prior.grants)`; of `swap-plugin` is `swap-plugin(prior.package,
prior.version, prior.hash)`. Each is another admin write with the row's
`prior` as its payload, so the prior DOCUMENT is reconstructible from the
ledger alone and `before` is what the inverse lands — proven across a
daemon reopen (§Invariant cases 3–5). This is the K7 lifecycle
(`operator-intent-no-inverse` in the bundle's metadata): no inverse in
any fiber's journal, nothing rolled back by anyone's teardown, history
the ledger's. What the inverse restores is the DOCUMENT; the runtime then
converges on it, and I4 says that state equals a fresh boot of it — so a
removed entry re-added is a NEW incarnation, its world journal already
withdrawn LIFO by the removal (I1), and the card says so rather than
promising a resurrection.

**Refused `irreversible`, typed, nothing written**, where no inverse can
be recorded as one write: `remove-entry` of an entry with CHILDREN (the
inverse would be a subtree; a removal is one entry, and the operator
removes leaves first — R10, no cascade through this contract);
`remove-entry` or `swap-plugin` of a RAW entry (undecodable, preserved
verbatim, R11 — its record cannot be captured as a typed `prior`, and it
is the file's to fix). **Refused `malformed`**: a record that does not
decode as an entry, an id that already exists on `add-entry` or does not
on the others, a `parent` that is not an entry, `config` not an object,
`grants` that would refuse at activation (the same `validate` + the
seat decoder's admission the document-led path applies — nothing more,
nothing less; whether admission enforces 01's attenuation law against
the parent is as today and not this card's), an empty `hash` (Law 5: an
entry names its pin). **Refused `conflict`**, retryable: an operation in
flight on the entry or the document (the engagement gate), a target
fiber not at rest, a withdrawal replay in flight, a faulted entry (the
`amend.rs` refusals, verbatim), and a `swap-plugin` whose `package` is
live under a DIFFERENT pin for another entry (the daemon holds one pin
per package, `applied_pins`; re-pinning it would silently replace every
sibling's artifact at its next activation — R9; the operator swaps them
together or names a distinct package). **Refused `unauthorized`**: an id
outside the caller's `entry-ids` scope (on `add-entry`, the NEW id and
its `parent`); the caller's own entry or an ANCESTOR of it, for every
write — self-widening is escalation (Law 1) and self-removal awaits its
own teardown from inside its own call (the K7 nested-dispatch class,
extended to the cascade).

**(c) `set-disabled` is a disposal, and the card does not pretend
otherwise.** `disabled: true` applies the `Disable` step — the fiber is
disposed, kernel registrations released, the entry's world journal
withdrawn LIFO (I1), the entry kept (`Loader::dispose_entry` already
does exactly this, persisting `disabled: true`). `disabled: false`
applies `Enable`: a fresh incarnation with an empty journal. The inverse
restores the document; I4 governs the runtime.

**(d) `patch-entry` refuses a patch whose result changes `config.grants`
— the side door closes, if round 1 confirms it is open.** `validate`
gains one check: the patched `grants` equal the committed `grants` by
value, else `refused("grants are jinn:profile-admin's")`, nothing
written, an `AmendmentRefused` row. `config.injects` stays patchable —
04: a declaration gates and never widens. **Why it rides, with reasons.**
(1) Same seam, same file, same test fixture as `set-grants`. (2) Zero
design freedom: 04 already states the rule in prose; the validator
merely lacks the check. (3) It cannot hide: its own red-first case, its
own commit, its own line on the meter. (4) A pin-bump that adopts this
card must audit every `patch-entry` caller in the distribution once.
**Why not, answered.** It is a tightening on 0.x: the M2-K13 and M2-K26
(e) precedents — a rule that was law in prose becomes a refusal without a
signature change, `jinn:profile` 0.2.0 → 0.3.0 additive. The harness's
UI-2 transport patches `config.data` only (its plan §9.5, by design), so
no first-party caller is refused; a `tests/invariants/` case that patches
grants through `patch-entry`, if one exists, is the verifier's to amend
on the lane and is named in round 1.

**(e) `swap-plugin` is an incarnation REPLACEMENT, and the window is
closed.** The fact at `655f07e`: the document-led `Replace` step
(`crates/jinnd-loader/src/apply.rs`) is `dispose_step` then
`spawn_step` — the old fiber is DISPOSED (`ExplicitDispose`: its world
journal withdrawn LIFO, its listens released outright, no tombstone),
then a fresh fiber spawns on the new package's lane. Two consequences:
the entry's fs writes are gone after a provider swap, and a
reply-expecting walk between the disposal and the successor's `listen`
selects nobody — the #47 shape, on "the one swap every seam proves".
The law reads the other way: the M2-K4 ruling (Decision Log 2026-08-28)
says *"incarnation replacement (reconcile/config-edit) hands the
successor the entry's live effect journal"*, `contracts/README.md`
§Lifecycle classification lists hot-swap among incarnation
replacements, R8 calls the Mode-1 swap the shape that keeps the old
instance's contribution, and I4 demands ONE quiescent state whichever
path produced it. **Ruled on the card:** `swap-plugin` — and, by I4 and
R10, the document-led `Replace` it shares a step with — is a
replacement of the SAME ENTRY: the old instance's world journal is
inherited by the successor (`LaneCore::inherit`, the K4 mechanism), its
listens entomb at the suspension (M2-K26 (a)), the successor activates
STAGED and commits through `rebind` under one lock (M2-K26 (b)), and a
reply-expecting walk in the window is refused `restarting` — never
answered unmodified. Recommended shape: the `Replace` step suspends the
old fiber as a replacement and spawns the successor under the same entry
on the new lane; the tombstone set is keyed by ENTRY (the shape K26
recommended: "ONE `rebind` call replaces an entry's tombstones") so the
successor's commit replaces exactly them; the old fiber's rest does not
withdraw tombstones a successor is owed. The fiber engine is not
touched: no new cause, no `Owed` arm. **STOP RULE (e):** if closing the
window requires the fiber engine to learn a cross-fiber `Reload`, a new
`TransitionCause`, or an `owed.rs` arm, or if an existing
`tests/invariants/` case pins dispose-on-replace, STOP and escalate with
the loom model priced — a scoping ruling is the COO's — **PRE-RULED (COO ruling, 2026-09-04):
do not wait for it.** On any of those four conditions the implementer
takes the fallback IN THE SAME ROUND: the five writes ship with `Replace`
as it is today; an invariant case PINS the window and the journal loss
as a stated limit (case 7 in its limit form); (e)'s replacement
semantics become card **M2-K27** with the loom model priced; the split is
posted on the Todo and the round continues. A round is never lost to
this.

**Concurrency with the file (R1).** An admin write and a watcher-led
reconcile exclude each other through the loader's engagement gate as
`patch-entry` does today (`M1-P6b`, loom-modelled in `gate.rs`); an
admin write refused `conflict` is retryable; a file edit that lands
between the write's commit and its echo is the next reconcile's, never
lost (LAW §3). `add-entry` and `remove-entry` change the tree, so they
engage the DOCUMENT, not one entry; the other three engage the entry.

## Facade delta

**ONE additive item and its enum, authorized here before use:**

```
LedgerEventKind::ProfileAdministered {
    entry: EntryId,          // the administered entry
    by: String,              // the caller entry, or peer:<id>
    write: ProfileWrite,     // which of the five
    before: String,          // sha256 hex of the rendered document before
    after: String,           // sha256 hex after — equals the file's digest

pub enum ProfileWrite { Add, Remove, SetDisabled, SetGrants, SwapPlugin }
```

**Where it lives (COO ruling, 2026-09-04; R10):**
`crates/jinnd-api/src/ledger.rs` is already over the 300-line cap
(pre-existing, PLA-363), so the new kind's payload types go in a NEW file
under `crates/jinnd-api/src/ledger/` (beside `record.rs`), re-exported so
every path stays what it was; `ledger.rs` gains the enum arm and nothing
else. Every touched `src/` file is ≤ 300 lines after; `wc -l` before
submitting. `AmendmentRefused`, `GrantRefused`, `WriteBack`,
`FiberTransition`, `EffectWithdrawn` already exist and carry the rest. A second facade item
the implementer finds necessary is a STOP-and-escalate with the item
named (the M2-K20 rule); an unauthorized one is an automatic Blocker
(two-key).

## Invariant cases the verifier will own (named here, written by the verifier; each red first)

Homes are the verifier's call. The fixture: the real daemon over a
profile with an ADMIN guest (granted `jinn:profile-admin` `["*"]`), a
SCOPED admin (granted `["target"]`), a VIEWER (`jinn:profile` reads
only), and two target packages with distinct hashes; a ledger read; the
file's digest read from disk with nothing but the file.

1. `an_admin_write_without_the_grant_is_refused_before_any_effect` —
   the viewer's `resolve` of `jinn:profile-admin` is the broker's
   `GrantRefused`; the scoped admin's write outside `["target"]` is
   `unauthorized` on the wire and `GrantRefused { ScopeMismatch }` on the
   record; the document digest is unchanged; zero transitions.
2. `each_of_the_five_writes_lands_one_row_with_the_caller_and_both_digests`
   — add, remove, disable, grants, swap, in turn: exactly one
   `ProfileAdministered` under the ADMIN's entry, `before` ≠ `after`,
   `after` == the on-disk file's SHA-256 read independently, `prior`
   equal to the `entry(id)` read taken before the write, `None` on add.
3. `an_add_is_reversed_by_its_recorded_remove_across_a_daemon_reopen` —
   add; reopen the daemon; `remove-entry` with the row's id; the digest
   returns to the first row's `before`; the composition equals a fresh
   boot of the original document (I4).
4. `a_removal_is_reversed_by_re_adding_the_recorded_prior_across_a_reopen`
   — the mirror of 3, `add-entry(prior)` verbatim from the row.
5. `a_swap_is_reversed_by_the_prior_pin_across_a_reopen` — swap to the
   second hash, reopen, swap back with `prior`; digests round-trip; the
   entry's incarnation count reads two replacements on the record.
6. `a_removal_withdraws_exactly_the_entrys_contribution_and_nothing_else`
   — I1/R11: the removed entry's listens, alarms and sockets released,
   its fs writes reverted LIFO with `EffectWithdrawn` rows; a sibling's
   registrations and files untouched; a sibling that INJECTS the removed
   provider reloads by M2-K24, nothing else moves.
7. `a_swap_window_is_closed_to_reply_expecting_walks_and_the_journal_is_inherited`
   — (e): a slow successor by construction; every walk in the window is
   `DispatchRefused { owed: Reload }` / `restarting`, ZERO
   `DispatchTrace { listeners: 0 }`; the entry's fs writes from before
   the swap are present after it and revertible by key; the document-led
   file edit of the same fields lands the same quiescent state (I4 across
   the two paths). Under the (e) fallback this case pins the LIMIT
   instead and says so in its name.
8. `a_disabled_toggle_disposes_and_an_enable_boots_a_fresh_incarnation`
   — (c): `disabled: true` → `Disposed` on the record, journal withdrawn;
   `disabled: false` → a new fiber, empty journal, the file's flag
   flipped both times; the inverse round-trips the digest.
9. `a_grants_change_lands_only_through_a_restart_never_live` — R9/04: the
   entry's live incarnation keeps its old grants until `ConfigChanged`
